This document is an illustration-first crosswalk. On the left are the reconnaissance targets that kwara (an operator-attribution forensics toolkit specialised in the digital-advertising ecosystem) actually collects — URL parameters, HTML pixels, third-party requests from HTTP Archives, ads.txt monetisation declarations, TLS certificates, HTTP headers, cloaking behaviour differentials; the right column shows what each of these originally is inside the digital-advertising industry — artefacts that SSPs, DSPs, DMPs, ad exchanges, IAB transparency standards and conversion-tracking pixels manufacture for their own commercial purposes, artefacts that are deliberately public or impossible to erase.

Put the two columns side by side and a recurring structure emerges: to make money flow correctly, conversions count correctly, and the supply chain auditable by buyers, the advertising ecosystem laid a whole machine-readable layer of identifiers and declaration files across pages and protocols. The operators of scam and coordinated networks monetise inside this very ecosystem, and therefore have no choice but to carry the same set of identifiers. kwara's job, in essence, is to sample at a few fixed junctions of this advertising machine, then aggregate identical identifiers across domains into evidence of a common operator.

1. The big picture: the ad ecosystem and kwara's sampling points

Programmatic advertising is a supply chain that runs from the advertiser (where the money starts) through buy-side technology, the marketplace and sell-side technology, down to the publisher (where the money ends), with every intermediary taking its cut [1][2]. The diagram below flattens that chain and marks, in amber, where kwara samples. The key observation: kwara never needs access to the inside of an exchange or SSP — it samples only at the end visible to the user's browser (URL, HTML, third-party requests) and in the declaration files publishers publish themselves (ads.txt), and can still infer the account identities at the other end of the supply chain.

3. URL parameter layer ↔ click IDs and campaign attribution

When a user clicks an ad, the ad platform automatically appends a click ID to the landing-page URL — Google's gclid, Meta's fbclid, TikTok's ttclid, Microsoft's msclkid [12][14][16]. This parameter is the bridge between the ad side (campaign / ad group / bid) and the site side (the pixel's conversion events). The pixel on the landing page captures the click ID and writes it into a first-party cookie (e.g. Meta's _fbc), then reports back through the Conversions API so the conversion is attributed to the correct ad account [15]. utm_* is the human-readable labelling left over from Google's 2005 acquisition of Urchin [17].

kwara's param_attribution.py ships this entire click-ID / UTM lookup table as built-in constants: identify_param() maps utm_* to Google Analytics, fbclid to Meta, gclid to Google Ads. On top of it sit two deliberately separate aggregation functions:

  • shared_params(key, value) — same campaign: two posts carrying the same value (e.g. ?utm_term=145) = the same campaign. Overlong opaque tokens (JWTs, encrypted affiliate IDs) are compared by SHA-256 prefix instead.
  • shared_param_keys(key, *) — same backend: the operator hands every victim a unique ?aff_id=A1, A2, A3… — every value appears exactly once, yet the existence of the key itself points to a single backend system. Three thresholds (minimum posts, minimum distinct values, maximum domains) filter out generic keys like ?q=.

4. HTML pixel layer ↔ measurement / monetisation tags

Technically, a “pixel” or “tag” is a piece of JavaScript plus a network beacon (a tiny request used to send data home); the name “pixel” is a relic of the early 1×1 transparent image, which today survives only as a <noscript> fallback [18]. The forensically crucial property: account / property identifiers are hard-coded as string literals inside the initialisation call, with no obfuscation — the vendor's script must be able to read them, so anyone who views source can read them too:

  • Meta: fbq('init', '<pixel-id>') — bound to a specific Meta ad account in Events Manager [18]
  • GA4: gtag('config', 'G-XXXXXXXXXX'); in legacy UA UA-XXXXXXX-X the middle segment is the account number, shared across every property of one owner [19]
  • Google Ads: AW-XXXXXXXXX (unique per Google Ads account); AdSense: ca-pub- + 16 digits, written in ads.txt as pub-, i.e. the publisher account that receives the money [20]
  • TikTok: ttq.load('<id>'); LINE: _lt('init', {tagId:'…'})

kwara's fingerprints.extract_tracking_ids extracts by pure regex, no JS engine, currently covering 11 platforms. Two review-hardened design fixes matter: (1) context-anchoring — every pattern requires the ID to appear inside a real invocation (an gtag/fbq/ttq call or a vendor host URL), to avoid catching documentation examples; (2) placeholder filtering — dropping placeholder strings like G-XXXXXXXX. The aggregation function shared_tracking_ids admits a cluster when the same (platform, ID) spans ≥2 domains.

Why this is one of the strongest signals.A pixel ID is tied to the operator's money and measurement: AdSense ca-pub- is a payee account; Meta Pixel and AW- bind billing and conversion attribution — the accumulated conversion history, optimisation learning, audience lists and payment relationships all hang off that account. Rotating a domain is free and instant; rotating an account forfeits all of it. Operators therefore rotate domains far more often than IDs — so IDs outlive domains and betray the cluster.

5. ads.txt layer ↔ IAB supply-chain transparency

ads.txt (Authorized Digital Sellers) is a plain-text file introduced by IAB Tech Lab in June 2017 to combat domain spoofing and counterfeit inventory; the publisher places it at the domain root, declaring line by line who is authorised to sell its ad inventory[23][24]. Four fields per line:

FieldContentForensic meaning
① Ad system domainCanonical domain of the SSP / exchange (e.g. google.com) Which SSP is selling this inventory
② Publisher account ID (seller_id)The publisher's account identifier inside that SSPTies the site to one account on a named SSP
③ RelationshipDIRECT or RESELLERDIRECT = the site owner is paid directly; RESELLER = a third party is authorised to resell
④ Certification authority ID (optional)TAG IDAuxiliary verification

ads.txt alone gives only anonymous account IDs; the other half is sellers.json — published by each SSP at its own root, resolving seller_id back to named entities (name + domain + seller_type) [25][8]. Combine the two and an investigator goes: domain → ads.txt authorisation list → (per SSP) sellers.json reverse lookup → real payee identity. At runtime there is also the OpenRTB SupplyChain object recording the intermediary path hop by hop (asi/sid aligned with sellers.json)[26]. ads.txt 1.1 (2022) adds the OWNERDOMAIN/MANAGERDOMAIN self-declaration variables.

kwara's adstxt.py fetches, for every landing domain, /ads.txt, yielding two operator signals: (1) DIRECT accounts shared across domains (frequency weighting required — the few accounts shared by every domain are common monetisation intermediaries, not one operator); (2) byte-identical ads.txt (same raw_sha256) = a shared template, the strongest operator signal. By design ads.txt is harder evidence than GA4 sharing: GA4 is an unconscious tracking leak, whereas ads.txt is a deliberate monetisation declaration. Even 403s (some cloakers WAF-block the ads.txt path too) are recorded rather than dropped — the status itself is a cloaking-adjacent OPSEC signal.

6. HAR endpoint layer ↔ the third-party tracker graph

While screenshotting a landing page, Playwright also records every third-party request domain the page makes (the core data of an HTTP Archive / HAR). shared_endpoints() surfaces non-allowlisted third-party endpoints called by ≥2 landing domains — typically the operator's backend API or self-hosted analytics server. Behind this capability stands a whole academic web-measurement infrastructure: Englehardt & Narayanan's million-site measurement (OpenWPM, CCS 2016)[29], and the tracker→parent-company entity-resolution databases of WhoTracks.Me and Disconnect [30].

7. Certificate / infrastructure layer ↔ Certificate Transparency

Beyond advertising identifiers, a network can be clustered through the infrastructure that carries its traffic. Certificate Transparency (CT) is the public, append-only log of every certificate issued by trusted CAs, published in near real time — letting analysts discover and pivot to newly issued domains [31]. Threat-intel pivoting techniques include shared issuer+serial, overlapping SANs (one cert covering multiple related domains) and issuance-time patterns, combined with passive DNS and ASN co-location for graph clustering.

8. HTTP header layer ↔ origin / WAF deployment

This layer is not advertising-specific; it is the traces left by the servers that carry the ad pages. The scanner stores the full response headers of every redirect hop in redirect_hops.response_headers_json, header_analysis.py provides four orthogonal views. The key: origin response headers are not scrubbed by the Cloudflare proxy, so this signal sees through CDN cloaking:

  • per_domain_constants: headers that always appear, with stable values, across repeated scans of a domain. For instance a domain that keeps returning a non-standard custom header (such as x-server-hosted: …) — exposing the real origin behind Cloudflare.
  • cross_domain_shared_template: multiple domains carrying the same (anomalous, non-default) header values = one server deployment template, evidentiary weight on par with GA4 sharing.
  • detect_fake_versions: matched against a table of known non-existent versions (Apache 2.5.1, PHP 9.x…); a hit means the operator is actively fabricating the fingerprint — an active anti-detection signal.
  • cookie_origin_signals: Set-Cookie; Domain=.realorigin leaks the origin; flag-setting consistency is itself a cross-domain fingerprint.

9. Cloaking & OPSEC layer ↔ ad / SEO fraud countermeasures

Cloaking — serving crawlers / reviewers (Googlebot, ad-platform review bots, Facebook's crawler) different content from what real users see — is how scam sites and made-for-advertising (MFA) operators dodge search and ad review at once, and detecting it is itself an attribution signal. The academic foundation: Wang & Savage's Cloak and Dagger (CCS 2011) defined the taxonomy of user-agent / redirection / IP cloaking [32]; Google's Cloak of Visibility (IEEE S&P 2016) found 11.7% of top-100 Google search results led to cloaked content [33]. The common core of every detection method is cross-view comparison: fetch the same URL repeatedly with different UA / referrer / IP, follow every redirect hop, and flag whichever content or redirect chain diverges.

OPSEC path layer (opsec.compute_opsec_profile) is the same logic from another angle: compare the success rates of the lightweight HTTP fetch versus the Playwright capture path. “Blocks plain UA but admits Chromium” is a specific WAF deployment template; multiple domains in one case sharing the same OPSEC level, independently of GA4 / TLS / parameter signals, points to the same operator. E.g. within one case some domains block both capture paths while others admit both — a split independent of GA4 / TLS signals, yet pointing to the same operator boundary.

10. The through-line: stickiness and cross-confirmation

The entire document collapses into one principle: identifiers that exist to earn or to measure (AdSense ca-pub-, analytics IDs, ads.txt account IDs) and infrastructure that exists to carry traffic (certs, IPs, ASNs) both carry a high rotation OPSEC cost — a new AdSense account must pass review again, a new certificate leaves a fresh pivot point in CT, and splitting tracking across accounts wrecks the operator's own revenue and analytics. Threat-intel practice keeps finding that operations are rarely unmasked by exotic detection; they are unmasked by identifier / infrastructure reuse and overlooked metadata [34].

But stickiness is not proof. A shared ID may merely reflect common hosting by a management company / agency rather than a single malicious owner — the known false-positive pattern in the ads.txt dark-pool literature, and the reason kwara frequency-weights shared ads.txt accounts. Worse, IDs can be planted — anyone can put someone else's GA / AdSense ID on a site they control to forge a link. The strongest attribution is therefore stacking multiple mutually independent sticky signals, never betting on a single ID.

This is the design motive behind kwara's ad_tracking_platforms() and its signal_source status. For every platform it inspects URL-parameter evidence and HTML-pixel evidence side by side, yielding four states, and both must require the URL and HTML evidence to intersect on the same ua_id or domain — this is the watershed between “both signal types present” and “the two signals cross-confirm”, and it is a contract that must be kept. Mislabelling the former as the latter is the UI lying to the analyst.

11. Limitations and the contracts that must be kept

  • GA4 weakened the classic UA pivot.Legacy UA-XXXXXXX-X IDs cluster directly on the middle account number; GA4's G- and GTM lack an owner-revealing suffix and are less catalogued, pushing researchers toward Wayback history and other signals [21].
  • Planting and false flags (placing someone else's identifiers on your own site to forge a link).Both IDs and infrastructure can be deliberately planted to fabricate associations; shared / commoditised infrastructure also produces spurious edges. Attribution must stack independent signals and state its confidence.
  • The latest-usable snapshot contract.Pixel / HAR aggregation takes the latest usable snapshot” (capture_status='ok' and non-empty), never simply the newest — otherwise one re-capture that failed a Cloudflare challenge would silently bury earlier good evidence. Applies to shared_tracking_ids, ad_tracking_platforms, shared_endpoints.
  • The behaviour layer deliberately asserts no “coordinated” flag.Any coordination threshold tuned to a single dataset overfits; kwara outputs only the raw distributions (first/last_posted, span, interval, actor_count) and leaves interpretation to the analyst's cross-case context.
  • Verifiable beats algorithmically clever.Every cluster ships with its domains / urls / posts list, so a third party holding the ZIP evidence pack can reproduce what they see without trusting kwara — or the analyst.

12. So what can this tool do, and where does its irreplaceability lie?

The previous eleven sections in one sentence: kwara's value lies in no single signal, but in stacking the mutually independent “sticky” traces of the ad ecosystem, cross-confirming them, and packaging the result as evidence reproducible without trusting the tool or the analyst.Any single sampling point — a pixel ID, an ads.txt DIRECT line, a certificate — other tools can look up too. What is genuinely hard to replicate is joining all six layers into a single case's attribution while holding both lines at once: no false accusation, and full reproducibility.

What it can do

  • Turn a pile of suspicious shortlinks into a same-operator evidence graph.Sample at six fixed junctions, join across domains on canonical constants, and cluster superficially unrelated domains into one operator.
  • Cross-confirmation, not single-point conjecture.both The contract requires URL evidence and HTML-pixel evidence to intersect on the same ua_id or domain before anything is promoted to “independently confirmed” — the line that separates “both signal types present” from “the two signals corroborate each other”.
  • Read out active evasive intent, not just fingerprints.Cloaking, fabricated headers and OPSEC gating show the operator wrote logic to deliberately dodge review — a judgement one rank above unconscious fingerprints.
  • Built-in false-positive protection.Frequency-weights shared monetisation accounts and explicitly flags planting and false-flag risk, so agency / intermediary sharing is not mistaken for a single operator.
  • Produce a verifiable evidence pack.Every cluster carries its domains / urls / posts list; a third party with the ZIP can walk back to the raw evidence and reproduce it — no trust in kwara, and none in the analyst, required.

Glossary

SSP Supply-Side Platform
Software that lets publishers manage, optimise and sell inventory across multiple demand sources; the sell side.[1]
DSP Demand-Side Platform
Software that lets advertisers / agencies buy inventory automatically across sources, deciding bids in real time; the buy side.[1]
DMP / CDP Data Management / Customer Data Platform
The audience-data layer. DMP = anonymous, third-party, short-lived, built for reach; CDP = named, first-party (incl. PII), durable, built for retention.[10]
Ad Exchange Ad exchange
The neutral marketplace matching supply and demand via real-time bidding (analogy: SSPs / DSPs are brokers, the exchange is the stock exchange).[1]
Ad Server Ad server
Two kinds: publisher-side (decides which ad runs and renders it, e.g. Google Ad Manager) and advertiser / third-party-side (hosts creatives, counts independently across sites).[6]
RTB / OpenRTB Real-time bidding
The mechanism by which a single impression is auctioned at page load; OpenRTB is the IAB's JSON standard, the whole loop bounded by tmax, completing in ~100 ms.[9]
ads.txt / sellers.json / SupplyChain object
The IAB supply-chain trio: ads.txt (domain side declares authorised sellers), sellers.json (SSP side resolves account IDs to names), SupplyChain object (runtime hop-by-hop path).[23][25]
Pixel / Tag / CAPI
Web-side JS + beacon tracking code with the ID hard-coded in the HTML; CAPI (Conversions API) is the server-side complement that bypasses ad blockers.[18]
Click ID gclid / fbclid / ttclid
The click identifier that ad platforms automatically append to landing URLs, attributing clicks to a campaign / ad account.[12]
MFA Made-for-Advertising
Sites built purely to arbitrage cheap traffic into ad impressions; they habitually reuse the same batch of analytics / pixel / ads.txt IDs and are therefore graph-clusterable.[28]
Certificate Transparency (CT)
Public append-only logs of certificates issued by trusted CAs; threat intel pivots on SAN overlap and issuance timing to track domains.[31]
Cloaking
Serving crawlers / reviewers different content from real users, to dodge search and ad review; detected by cross-view comparison.[32]
